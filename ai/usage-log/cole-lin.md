### 2026-10-28 — Re-syncing the shipper for a bound only the store was applying (PR #157)

- Tool and mode: Claude Code (Claude Opus 5), review and debug.
- Usage scenario: A finding on PR #129 showed that the shipper bounded no field at all while the log store bounds seven of them plus two enums, so one over-long field kept a whole line out of the searchable store. This service's copy of the shipper carries the same code, and this service is what makes it reachable: `path` comes from the URL, so a caller picks its length.
- Prompts (exact):
  - "is 129 ready?"
  - "yes do the round"
- Key response: Re-copied the canonical shipper, which now brings every field the store bounds inside that bound before writing the line. For this service the live case is `path`: a request to `/locations/` followed by 500 characters produces an `access_denied` line the store would have refused outright, leaving the only record on this container's stdout. `path` and `event` are cut and marked; ids, `method`, `role`, `status` and `durationMs` are left out instead. The `requestId` this service accepts from `x-request-id` is capped at 128 characters already, so it was never the exposed one.
- What I changed or rejected: Took the canonical copy wholesale rather than hand-applying the change here, and checked the two bodies are byte-identical afterwards — the file's own contract is that a change there is repeated here, and the last five rounds of hardening are exactly what a hand-applied patch loses. The reasoning behind each clamp, and the one finding I disagreed with, are recorded in the entry for PR #129 rather than repeated here.
- Second round the same day: re-copied again after a further finding on the canonical shipper. Its local write — `console.log`, or a `write` function a service hands in — sat outside the guard that exists so `emit()` cannot throw, so a sink that fails threw into the request being logged. This service is where that lands: every `access_denied`, `jwks_unavailable` and `unhandled_error` line is written on the request's own stack, and in a container stdout is a pipe, where a Linux write is synchronous and a reader that goes away raises `EPIPE` there and then. The reasoning is in the entry for PR #129.
- Third round the same day: re-copied once more. The fallback line - the one the shipper writes when a caller's object cannot be read at all - carried no `requestId`, so the only record that a log call failed could not be tied to the request it failed on. That matters here more than anywhere: every `emit()` in this service passes `requestIdOf(req)`, and the three events it writes are `access_denied`, `jwks_unavailable` and `unhandled_error` - the three a reader goes looking for by request id. The id is read in its own `try` exactly as the event name already was, and bounded, so it cannot itself be the reason the line fails too; it is the Kafka key as well now, so the failure lands in the partition already holding that request's lines. One existing test in the canonical spec asserted the old behaviour, no key on a fallback, and was changed rather than worked around: it documented what the code did, not a decision anyone had taken.
- Fourth round the same day: re-copied again. Three more findings on the canonical shipper, all the same class as the local write from the round before - a caller-supplied part of `ShipperOptions` running outside the guard. `newId` sat in the same statement as that write, one argument along, and ran before the guard, so an exception from it escaped `emit()` entirely; the default stands in now and a counter says it happened. `flushMs` is refused at construction unless `setInterval` can schedule it, because anything else becomes a flush loop for the life of the process. And the service name, validated once in the constructor, was reread from the caller's object per line - this service's `src/common/log.ts` passes a literal, so nothing here could hit it, but the shipper is copied into every service and the next caller may not.
- Fifth round the same day: re-copied once more, for two findings in the redaction walk. Metadata strings now have removed from them what the store's JSONB cannot hold - a NUL, an unpaired surrogate - because either one cost the whole line at the insert rather than the one field; this is what the round before did for `method` and `path`, one level further down. And arrays are rebuilt by index instead of with `value.map`, which goes through `Symbol.species`: a subclass of `Array` came back as itself, so `JSON.stringify` called its inherited `toJSON` after redaction had finished and could return anything. Dropping own function values does not help, because a class puts `toJSON` on the prototype where `Object.entries` never looks. A caller's overridden `map` no longer runs in the walk either.
- Sixth round the same day: re-copied once more, for two findings in the shipper. Guarding the *call* to `newId` had not been enough - `this.options.newId` is itself a property read on an object the caller still owns, and `this.options.publisher` in `emit()` sat outside any guard at all - so every option is held in a field at construction now, and after that there is nothing of the caller's object left to read. That closes the class rather than one more instance of it. And `newId`'s result was unchecked: `lineId` is the one envelope field that can be neither dropped nor cut, because the store requires a UUID of it, so a generator returning a counter would have cost every line this service writes. It falls back to a real one and counts.
- Verification: `npm test` in the Supplier Service (229 passed) and `tsc --noEmit` clean. The behaviour itself is covered by the canonical copy's spec in the Logging Service, which checks a written line against `inboundLineSchema` itself rather than against a copy of its numbers; of the 53 cases added across the last five rounds, 48 fail against the unfixed shipper. The two copies were compared byte for byte afterwards, and against the copy on the PR #129 branch, so the overlap resolves to the same content whichever merges first.
